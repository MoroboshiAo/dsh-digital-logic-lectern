# 讲稿：补码为什么能把减法变加法（4 分钟）

## 结论

补码把减法换成加模补数，进位越过字长后被硬件丢掉，结果自然正确。

## 板书

1. 8 位字长的模是 256
2. −5 的原码 10000101
3. 反码 11111010，末位加一得补码 11111011
4. 3 − 5 改写成 3 + 251
5. 251 的二进制正是 11111011
6. 相加得 254，第 8 位之外的进位丢弃
7. 254 读作 −2，与直接相减一致

## 推导口播

第一步先立规矩：8 位只能表示 0 到 255，超出的部分不是错误，而是被硬件自动丢掉。第三步要讲清楚，反码到补码只差末位加一，这是两个不同的概念，不是同一个东西的两种叫法。第四步是整节课的转折点，减法并没有被消灭，它被换成了加法，所以加法器一种电路就够了。第五步停下来，让对方把 251 和 11111011 对上，确认这不是巧合。

第六步要强调进位的身份：它不是溢出错误，而是模运算的必然结果，硬件本来就不保存第 9 位。第七步回到十进制，不要自己说出 −2，让对方读。学生最容易卡在第四步，因为他们习惯把 251 当成一个普通的正数，而不是 −5 在模 256 下的另一种写法。

## 反例

有人以为补码就是反码。拿 −5 现场比一次：反码是 11111010，补码是 11111011，差的那一位就是全部区别，这一步不能靠背。

还有一个更有力的反例：−128 在 8 位补码里能表示，却没有原码，也没有反码。这说明"反码加一"只是计算补码的一条路径，不是补码的定义。

## 仿真佐证

现场运行 node scripts/dltool.js code --bits 8 --value -5，工具会输出原码、反码、补码、移码四行，并给出表示范围 −128 到 127。讲稿里出现的每个位模式都来自这次输出，不是手写，也不是背下来的。

## 收口提问

8 位补码里 10000000 表示几？

标准答案：−128。

错答一：128，忽略了符号位。

错答二：0，误以为全零取反后还是零。
